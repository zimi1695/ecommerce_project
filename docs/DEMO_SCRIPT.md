# 系统演示路线（完整版）

> 时长约 15~20 分钟。真实模式 = 本地 `http://localhost:5173`（600 万真实事件）；在线版 = https://zimi1695.github.io/ecommerce_project/ （Mock，页面数字与真实一致，可作备份）。
> 演示对象均为真实库固定记录，切换模式数字不变。

## 演示前检查（开场前 5 分钟）

```bash
wsl -d Ubuntu bash /home/li177/ecommerce_project/scripts/check_status.sh
# 预期：MySQL Up / 后端 active / 前端 active / 两个 HTTP 200
```

异常处理见文末"应急备案"。

## 第一幕：开场规模（数据总览）

打开 `http://localhost:5173`（数据总览页）。

讲法：**这不是演示数据，是 6750 万行原始数据里已入库的前 600 万条真实行为**（2019 年 11 月整月）。

页面数字（现场指认）：
- 行为事件 5,997,478；独立用户 748,770；商品 119,243；类别 618；品牌 3,241
- 对应原始数据集的 369 万用户 / 19 万商品——ETL 清洗与去重后规模略有收敛

加分点：切到 github.io 在线版对比——**页面数字完全一致**（演示用户 781/265、演示 Session 504、演示商品 22）。说明合成演示数据是按真实分布构造的，平时不用启动数据库也能展示。

## 第二幕：数据建模的证据（商品探索）

商品目录页。

1. 翻 1~2 页 → 指出 `category_code` 大量为空（真实缺失率 32.4%），说明**建模时必须允许 NULL**
2. 查 **1000978**（演示商品）：双品牌 samsung + lenovo → 这就是**桥表 product_brands 的证据**：真实数据里 136 个商品有多个品牌，不能强行绑一个 brand_id
3. 查 **7003278**（备选多品牌案例）：童车类，coballe + joie 双品牌，112 条事件
4. 点开 1000978 统计：22 次浏览、0 加购 0 购买 → **"price 不在商品表"的证据**：价格挂在事件上，22 次浏览价格各不相同，展示"行为发生时价格"

讲法：表结构不是拍脑袋定的，每个决策都有全量数据扫描背书（可展示 `scripts/analysis/01-07` 验证脚本）。

## 第三幕：一个用户的完整故事（用户行为）

用户页查 **564068124**。

**爆点：这个演示用户就是全库购买冠军**——781 条行为，265 次购买，累计消费 77,703.89（全库第一，第二名 46 次购买，差距近 6 倍）。

1. 默认列表看行为流水（浏览→加购→购买混合，倒序）
2. 切"购买"筛选 → 265 条全部为购买
3. 指认一条 **1005115（Apple 手机，921 元）**的重复购买模式——她反复买同一款
4. 点进某条记录的 Session → 跳转 Session 轨迹页

讲法：这就是运营视角的用户画像——单用户全生命周期行为在一页看完，分页与筛选都是数据库层 SQL 完成的。

## 第四幕：Session 轨迹（行为时间线）

两条路线任选或都演：

**A. 演示 Session `4488e77a`**（从第三幕跳转进入）：
- 504 条事件全为浏览，2019-11-01 03:38~07:15 UTC，**3.5 小时逛了 504 件商品**
- 讲法：单 Session 深度浏览的典型案例，每页 50 条时间线渲染

**B. 跨用户 Session `828b56d9-6c23-40b7-8825-173d58d33fe4`**（手动粘 URL）：
- 2 个用户、24 条事件（2019-11-03 18:09~18:22）
- **爆点：Session 居然关联了两个用户**——真实数据里 591 个 Session 是这样，所以 `sessions` 表**不能强绑 user_id**，这是红线第 4 条的活证据

## 第五幕：转化漏斗（分析页核心）

转化与排行页。

Session 口径漏斗（先讲口径再讲数字）：

- 浏览 → 加购 **3.68%**：133 万 Session 中 4.9 万产生加购
- 加购 → 购买 **54.2%**：加购后过半成交，"加购是高价值信号"
- 浏览 → 购买 **5.82%**

讲法（若被追问）：第一版用事件数相除得出超过 100% 的荒谬结果，修正为 Session 口径——**同一 Session 内是否出现该类行为**。页面有口径说明，前端也如实展示"不保证行为先后顺序"。

## 第六幕：排行与业务洞察（分析页下半）

切换三个维度各看 Top 10：

1. **商品榜**：1004856（samsung）62,457 事件 / 3,563 购买 / 销售额 457,966——全场流量王
2. **品牌榜**：samsung vs apple 双巨头争霸（3,241 个品牌里稳居前二）
3. **类别榜**：electronics.smartphone（演示类别 2053013555631882655）居首——**类别 ID 19 位超出 JS 安全整数**，前端用 json-bigint 无损解析（点开商品详情页看完整 ID 证明）

价格戏剧点（备用）：全库最高单价 2574.07（商品 21408160/21408165），最低 0.77——价格区间横跨三个数量级，所以 DECIMAL(10,2) 精度设计必要。

## 第七幕：工程闭环收尾（可选，技术评委向）

1. **幂等与断点恢复**：ETL 跑了 60 个 batch（600 万），中断后 `--resume` 跳过已成功批次续跑；`source_event_hash` 唯一约束挡掉 100,519 条完全重复事件
2. **性能**：conversion 曾要 37 秒（全表扫描 600 万行）→ 加覆盖索引 `(session_id, event_type)` 后 3.6 秒；Session 详情 0.02 秒——**索引前后的 EXPLAIN 对比可现场演示**（备选）
3. **质量门**：后端 37 个 pytest + 前端 8 单元 + 6 浏览器流程全绿；`scripts/frontend_check.sh` 一键回归
4. **协作证据**：GitHub Contributors 两人、CI 自动部署、Release 分卷数据——工程协作闭环

## 应急备案

| 突发 | 处理 |
|---|---|
| 前端挂了 | `wsl -d Ubuntu -u root systemctl restart ecommerce-frontend` |
| 后端挂了 | 同上换 backend；或 `journalctl -u ecommerce-backend -n 20` 看日志 |
| WSL 重启后服务没了 | `docker start ecommerce-mysql && wsl -d Ubuntu -u root systemctl start ecommerce-backend ecommerce-frontend` |
| 本机彻底不行 | 切 github.io 在线版（数字一致），口述"数据模式与本地图同" |
| 某接口慢 | 正常波动（总览 2.4s / 转化 3.6s 是冷查询，页面有加载态） |
